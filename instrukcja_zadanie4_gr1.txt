CZĘŚĆ 1: LABORATORIUM A (Projekt, Model, Baza danych, Strona HTML)

• KROK 1: Utworzenie struktury projektu Django
  1. Zainstalowano Django oraz bibliotekę Pillow.
  2. Utworzono projekt komendą:
     django-admin startproject config .
  3. Utworzono aplikację o nazwie 'katalog':
     python manage.py startapp katalog
  4. W pliku 'config/settings.py':
     - Dodano 'katalog' do listy INSTALLED_APPS,
     - Ustawiono ALLOWED_HOSTS = ['*'],
     - Skonfigurowano katalog szablonów (TEMPLATES: BASE_DIR / 'templates')
     - Skonfigurowano obsługę plików statycznych (STATICFILES_DIRS, STATIC_ROOT),
     - Ustawiono język polski ('pl') i strefę czasową ('Europe/Warsaw').

• KROK 2: Zaprojektowanie modelu danych i baza SQLite (Wymóg: min. 5 pól, min. 3 typy pól)
  W pliku 'katalog/models.py' utworzono model Manhwa posiadający 8 sensownych pól
  o 5 różnych typach pól Django:
  1. title (CharField) – pełna nazwa manhwy/komiksu.
  2. author (CharField) – autor i rysownik.
  3. genre (CharField) – gatunek (np. Akcja, Fantasy, System, Murim, Sport).
  4. description (TextField) – obszerny opis fabuły.
  5. chapters_count (IntegerField) – liczba rozdziałów.
  6. rating (IntegerField) – ocena czytelnika w skali 1-10.
  7. is_completed (BooleanField) – informacja, czy komiks jest zakończony (True/False).
  8. release_date (DateField) – data oficjalnej premiery.
  Model posiada czytelną metodę __str__() oraz metadane dla języka polskiego.

CZĘŚĆ 2: LABORATORIUM B (Endpoint API, fetch(), Aktualizacja DOM i Filtr)

• KROK 5: Zbudowanie endpointu API w Django
  1. W 'katalog/views.py' utworzono widok 'api_manhwa_list(request)'.
  2. Widok pobiera obiekty z bazy przez Django ORM (Manhwa.objects.all()).
  3. Zwraca odpowiedź w formacie JSON za pomocą klasy 'JsonResponse' o strukturze:
     {
       "items": [
         {
           "id": 1,
           "title": "Solo Leveling",
           "author": "Chugong, DUBU",
           "genre": "Akcja",
           "chapters_count": 179,
           "rating": 10,
           "is_completed": true,
           "release_date": "2018-03-04",
           "description": "..."
         }, ...
       ],
       "count": 7
     }
  4. W 'katalog/urls.py' zarejestrowano ścieżkę:
     path('api/manhwa/', views.api_manhwa_list, name='api_manhwa_list')
     oraz alias 'api/obiekty/' dla pełnej zgodności z poleceniem.

• KROK 6: Obsługa filtra po stronie Django ORM
  W widoku API pobierany jest parametr zapytania URL:
  - 'status' (np. ?status=completed lub ?status=ongoing) albo 'is_completed=true/false'.
  - Filtrowanie odbywa się bezpośrednio na poziomie bazy danych przez ORM:
    if status == 'completed':
        queryset = queryset.filter(is_completed=True)
    elif status == 'ongoing':
        queryset = queryset.filter(is_completed=False)
  Dzięki temu serwer zwraca do przeglądarki tylko wyselekcjonowane rekordy.

• KROK 7: Asynchroniczna komunikacja w JavaScript — funkcja fetch()
  W pliku 'static/js/main.js' zaimplementowano:
  1. Podpięcie zdarzenia kliknięcia pod przycisk "Wczytaj dane (fetch)" oraz zmiany w filtrze.
  2. Wysłanie asynchronicznego żądania HTTP GET:
     const response = await fetch(url);
  3. Weryfikację kodu statusu odpowiedzi za pomocą 'response.ok'.
  4. Odczytanie i zdekodowanie danych z formatu JSON za pomocą 'await response.json()'.

• KROK 8: Aktualizacja struktury DOM i obsługa stanów
  1. Stan ładowania: Wyświetlenie elementu #loadingStatus z animacją CSS przed wysłaniem
     żądania oraz jego automatyczne ukrycie w bloku 'finally'.
  2. Stan błędu: Przechwycenie wyjątków (catch) i wyświetlenie komunikatu w elemencie #messageBox.
  3. Stan pustej listy: Jeśli items.length === 0, poinformowanie użytkownika o braku pozycji.
  4. Bezpieczna aktualizacja DOM: Wykorzystanie metod document.createElement() oraz
     właściwości textContent zamiast innerHTML. Zapobiega to podatnościom XSS (Cross-Site Scripting).
  5. Wszystko odbywa się na żywo bez przeładowywania (odświeżania) okna przeglądarki!

6. ODPOWIEDZI NA PYTANIA KONTROLNE (Z PREZENTACJI)
--------------------------------------------------------------------------------

Pytanie 1: Czym różni się widok renderujący HTML od endpointu JSON?
Odpowiedź:
Widok renderujący HTML generuje pełną strukturę dokumentu za pomocą silnika szablonów
Django (funkcja render()), która jest interpretowana przez przeglądarkę jako kompletna strona.
Wymaga to przeładowania całego okna.
Endpoint JSON (np. api_manhwa_list) przetwarza dane z modeli ORM i zwraca czyste,
ustrukturyzowane dane w formacie tekstowym JSON za pomocą JsonResponse z nagłówkiem
Content-Type: application/json. Dzięki temu frontend może przetworzyć same dane i zaktualizować
wyłącznie wybrany fragment interfejsu (drzewa DOM) asynchronicznie.

Pytanie 2: Skąd endpoint pobiera rekordy i jaką rolę pełni ORM?
Odpowiedź:
Endpoint pobiera rekordy z relacyjnej bazy danych (w projekcie: SQLite, plik db.sqlite3).
Django ORM (Object-Relational Mapping) pełni rolę warstwy abstrakcji, która tłumaczy operacje
obiektowe w języku Python (np. Manhwa.objects.filter(is_completed=True)) na optymalne zapytania
SQL (SELECT ... FROM katalog_manhwa WHERE is_completed = 1). Pozwala to programiście operować
na obiektach Pythona bez konieczności ręcznego pisania surowego kodu SQL.

Pytanie 3: Co robi fetch() i co zwraca response.json()?
Odpowiedź:
Funkcja fetch() jest wbudowanym w przeglądarkę interfejsem JavaScript służącym do wysyłania
asynchronicznych żądań sieciowych HTTP bez blokowania głównego wątku przeglądarki. Zwraca
obiekt obietnicy (Promise), który rozwiązuje się do obiektu Response reprezentującego nagłówki
i stan połączenia. Metoda response.json() asynchronicznie odczytuje ciało odpowiedzi HTTP
i parsuje ciąg znaków JSON na natywne obiekty i tablice JavaScript (Promise<any>).

Pytanie 4: Dlaczego sprawdzamy response.ok?
Odpowiedź:
Funkcja fetch() odrzuca obietnicę (wchodzi do bloku catch) wyłącznie w przypadku krytycznego
błędu sieciowego (np. brak połączenia z Internetem, zerwany kabel, błąd DNS). Jeśli serwer
zwróci kod błędu HTTP, taki jak 404 (Not Found) lub 500 (Internal Server Error), fetch() nadal
uznaje to za udane połączenie! Właściwość response.ok ma wartość true tylko wtedy, gdy kod
odpowiedzi HTTP mieści się w przedziale 200-299. Sprawdzenie 'if (!response.ok)' pozwala
wykryć błędy serwera i prawidłowo poinformować użytkownika w interfejsie.

Pytanie 5: Jak JavaScript aktualizuje DOM bez przeładowania strony?
Odpowiedź:
JavaScript korzysta z interfejsu Document Object Model (DOM). Po odebraniu danych z API
skrypt nie wywołuje odświeżenia strony (location.reload()), lecz operuje bezpośrednio na
obiektach w pamięci przeglądarki. Za pomocą metod document.createElement('article'),
element.classList.add(...) oraz element.textContent = ... tworzy nowe węzły HTML i dołącza
je do drzewa dokumentu za pomocą metody parent.appendChild() lub replaceChildren().
Dzięki temu odświeżany jest wyłącznie obszar listy, a stan reszty strony pozostaje nienaruszony.

Pytanie 6: Dlaczego filtr danych powinien być obsługiwany również po stronie Django?
Odpowiedź:
Obsługa filtrowania po stronie backendu (w Django ORM) jest kluczowa dla wydajności
i bezpieczeństwa. Gdyby filtr działał wyłącznie w przeglądarce, serwer musiałby przesyłać
wszystkie rekordy z bazy (np. dziesiątki tysięcy pozycji), co drastycznie obciążałoby sieć
oraz pamięć urządzenia użytkownika. Filtrowanie w Django ORM ogranicza zapytanie SQL na poziomie
silnika bazy danych (klauzula WHERE), dzięki czemu przez sieć przesyłane są tylko te rekordy,
które użytkownik faktycznie chce zobaczyć.
